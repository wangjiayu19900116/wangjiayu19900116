# rtl-gen:需求 → 设计文档 → RTL(含 assert)→ lint → 验证方案

把一段模块需求(自然语言描述,或 .md/.txt spec 文件路径)按完整设计流程做成交付物。默认生成 SystemVerilog(`--verilog` 时 RTL 主体用 Verilog-2001,断言仍放在单独的 SV bind 文件中)。输出目录默认为当前目录,结构:

```
docs/<模块名>_design.md        设计文档
docs/<模块名>_verif_plan.md    验证方案
rtl/<模块名>.sv                RTL(每个模块一个文件)
rtl/<模块名>_sva.sv            断言模块(bind 方式,--verilog 时必用;SV 模式下简单断言可直接内嵌)
```

按以下六个阶段顺序执行,**每个阶段的产出是下一阶段的输入**,不要跳步直接写代码。

## 阶段 1:输入需求分析

从需求中提取结构化信息,欠定项按合理默认值补齐并**显式标注为"假设"**(默认:单时钟 `clk` 上升沿、同步低有效复位 `rst_n`、位宽/深度做成 parameter)。整理出:

- 功能一句话 + 输入输出数据流;
- 模块名、参数表、端口清单表(`信号名 | 方向 | 位宽 | 含义`);
- 时钟/复位域:几个时钟、是否跨时钟域、复位方式;
- 性能/时序要求:latency、吞吐、背压方式(valid/ready?);
- 边界与异常行为:满/空、溢出、非法输入时怎么办;
- **不确定项清单**:逐条列出"假设了什么、为什么"。

功能本身不明确(连做什么都提取不出)时停下来问用户;位宽、深度这类有默认值的不要问。

## 阶段 2:编写设计文档(docs/<模块名>_design.md)

基于阶段 1 的分析写设计文档,章节固定为:

1. **概述**:功能、应用场景、一句话数据流;
2. **参数与端口**:阶段 1 的两张表,加上每个端口的时序说明(相对 clk 的采样/驱动约定);
3. **设计方案介绍(详细)**:在给出微架构之前,先用完整的文字介绍整体设计方案——总体思路与架构选型(选了什么方案、备选方案是什么、为什么这样选,从时序/面积/复杂度角度说明取舍)、关键设计点逐个展开(如指针管理、满空判断、握手/背压处理、异常兜底等,每点说明"问题是什么 → 怎么解决 → 为什么可行");不要只给结论,要把推理过程写出来;
4. **微架构**:框图(用 mermaid 或 ASCII)、子模块划分、关键数据通路(各级流水线/寄存器站);
5. **状态机**:状态定义、转移图(mermaid stateDiagram)、每个状态的输出行为;
6. **关键时序**:典型操作的波形描述(可用 wavedrom json 或逐拍文字描述),明确 latency 和握手时序;
7. **复位与初始化**:复位后各寄存器的值、复位释放后首拍行为;
8. **假设与限制**:阶段 1 的不确定项清单原样放入。

文档写完后**自查一遍一致性**:端口表、状态机、波形三者互相对得上才进入下一阶段。

## 阶段 3:RTL 代码设计

动手写代码之前,先向用户完整展示本阶段的设计思考:逐个关键实现点说明候选做法、取舍依据和最终选择,其中涉及架构层面的结论要同步回填到设计文档第 3 章"设计方案介绍"中,保持文档与思路一致。

严格按设计文档实现,文档没写的行为不要擅自加;实现中发现文档有问题,先回去改文档再改代码。

**编码规范:进入本阶段写代码之前,必须先用 Skill 工具调用 `rtl-style` skill**,把完整规则(F/N/L/C/S/M/W/D/X 共十类带编号条款)加载进上下文并逐条遵循;与下面的要点冲突时以 rtl-style 为准。要点:

- SV 用 `always_ff`/`always_comb`/`logic`;Verilog-2001 用 ANSI 端口,时序逻辑一律 `<=`,组合逻辑一律 `=`;
- 组合块内所有信号先赋默认值,`case` 必带 `default`,**严禁推断出 latch**;
- 状态机三段式(状态寄存 / 次态组合 / 输出),状态用 `typedef enum` 或 `localparam`;
- 不用 `initial` 初始化寄存器、不用 `#delay`/`force` 等不可综合语句;
- 跨时钟域必须用标准结构(两级同步器、格雷码指针、脉冲同步),注释标出 CDC 边界;
- 信号命名:低有效 `_n`,寄存器输出 `_q`/`_r`;文件头注释写功能、参数、时钟复位约定、latency;
- 用户给的是已有工程时,先看现成代码的命名/复位/缩进风格并保持一致。

## 阶段 4:重点 check 点分析

实现完成后,系统地列一张 **check 点表**(放入验证方案文档,也是下一阶段写断言的依据)。逐类检查并记录"本设计是否涉及、风险在哪、如何验证":

| 类别 | 典型 check 点 |
|---|---|
| 协议/握手 | valid/ready 期间数据保持稳定;valid 不依赖 ready(避免死锁);req 必有 ack |
| 边界条件 | 满写/空读;计数器回绕;指针回绕;0/最大参数值的退化情形 |
| 状态机 | 不进入非法状态;无死锁状态(每个状态可达且可离开);复位回到 IDLE |
| 数据完整性 | 不丢数据、不重复、保序(FIFO/流水线类必查) |
| 复位 | 复位期间输出安全值;复位释放后首拍行为正确 |
| CDC | 同步器级数;格雷码单 bit 跳变;脉冲不丢失 |
| 溢出/非法输入 | 计算溢出截断策略;非法编码输入的兜底行为 |
| X 态 | 复位后无 X 扩散到输出 |

每条 check 点标注验证手段:**断言(A)/ 定向用例(D)/ 随机+覆盖(R)**,可多选。

## 阶段 5:增加 assert(SVA)

把阶段 4 中标 A 的 check 点逐条写成 SVA,**每条断言注释对应的 check 点编号**:

- 断言集中放在 `rtl/<模块名>_sva.sv`,用 `bind <模块名> <模块名>_sva sva_inst(.*);` 挂接(不侵入 RTL,综合工具自动忽略;`--verilog` 模式必须用这种方式);SV 模式下个别简单不变式也可用 `` `ifdef ASSERT_ON `` 内嵌;
- 并发断言统一模板:`assert property (@(posedge clk) disable iff (!rst_n) <属性>) else $error("...");`
- 典型写法:握手稳定 `valid && !ready |=> $stable(data)`;不满不溢 `!(full && wr_en)` 用 assume/assert 按方向区分;状态合法 `state inside {IDLE, RUN, DONE}`;计数范围 `count <= DEPTH`;
- 对关键事件补 `cover property`(如:发生过满、发生过背压下的写),供后续覆盖率收集;
- 断言要**可证伪**:不写永真式(如 `a |-> a`),每条想清楚"什么波形会让它 fail"。

## 阶段 6:lint 与验证方案

**lint:**

- 探测工具:`Get-Command verilator`、`Get-Command iverilog`;
- 有 Verilator:`verilator --lint-only -Wall rtl/<模块名>.sv`(bind 文件一并带上),警告逐条修掉,确需豁免的在代码处注明原因;没有 Verilator 但有 iverilog:`iverilog -g2012 -t null rtl/*.sv` 做语法/可综合性检查;两者都没有:明确告知"未做机器 lint",给出安装建议(`winget install verilator` 或 oss-cad-suite);
- lint 产物(编译产物等)放 TEMP 目录,不污染输出目录。

**验证方案(docs/<模块名>_verif_plan.md)**,章节固定为:

1. **验证目标与通过标准**:功能点全覆盖、断言 0 fail、代码覆盖率目标(如行/翻转 90%+);
2. **check 点表**:阶段 4 的完整表格(含 A/D/R 标注);
3. **TB 架构**:激励生成(定向 + 带种子随机)、参考模型/scoreboard 比对策略、监测点;
4. **用例清单**:每条定向用例一行(`用例名 | 对应check点 | 激励要点 | 预期结果`),随机测试的约束与种子策略;
5. **覆盖率计划**:功能覆盖点(covergroup 建议)、阶段 5 的 cover property 清单;
6. **工具与跑法**:推荐命令行(iverilog/Verilator/商用仿真器均给出),断言开关宏。

本 skill 默认**只交付验证方案,不实现 TB**;用户要求"把 TB 也写了"时,按验证方案第 3、4 章实现自检式 testbench(结束打印 `TEST PASSED`/`TEST FAILED (N errors)`)并实际跑通。

## 汇报

按阶段顺序汇报:关键设计决策(复位方式、latency、状态机)、文件路径清单、check 点数量与断言条数、lint 结果(0 警告或豁免清单)、以及**全部假设项**,提醒用户核对。不要宣称"综合/时序没问题"——只陈述实际做过的检查(lint≠仿真≠综合)。

## 注意

- 文档和代码必须一致:任何阶段发现矛盾,先改文档、再改代码、最后同步断言。
- 断言不是摆设:每条必须对应一个 check 点,且能被某个波形证伪。
- 输出文件若已存在,先确认再覆盖。
